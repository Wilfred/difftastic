# Contributing

## Building

Install Rust with [rustup](https://rustup.rs/), then clone the code.

```
$ git clone git@github.com:Wilfred/difftastic.git
$ cd difftastic
```

Difftastic uses [Cargo](https://doc.rust-lang.org/cargo/) for
building.

```
$ cargo build
```

Debug builds are significantly slower than release builds. For files
with more than fifty lines, it's usually worth using an optimised
build.

```
$ cargo build --release
```

## Common tasks

Difftastic uses a [`justfile`](https://github.com/casey/just) to collect
common developer commands. If you have `just` installed, run `just
--list` to see them all. Handy recipes include `just doc` (build and
serve the manual), `just compare` (run the output regression test), and
`just release` (tag and publish a release).

You don't need `just` to work on difftastic — the underlying commands
are described below — but it's the quickest way to discover them.

## Manual

This website is generated with
[mdbook](https://github.com/rust-lang/mdBook/). mdbook can be
installed with Cargo.

*Note: difftastic uses an older Rust toolchain version. You have to run `cargo install mdbook` outside of the repository directory. Otherwise, installation fails.*

```
$ cargo install mdbook
```

You can then use the `mdbook` binary to build and serve the site
locally.

```
$ cd manual
$ mdbook serve
```

Alternatively, run `just doc` from the repository root to build, serve,
and open the manual in one step.

## API Documentation

You can browse the internal API documentation generated by rustdoc
[here](https://difftastic.wilfred.me.uk/rustdoc/difft/).

Difftastic's internal docs are not available on docs.rs, as it [does
not support binary crates today](https://github.com/rust-lang/docs.rs/issues/238).

## Testing

Run the test suite with Cargo.

```
$ cargo test
```

Some tests rely on the system MIME database and are ignored by
default. CI runs them too, so it's worth running them locally:

```
$ cargo test -- --ignored
```

The best way to test difftastic is to look at history from a real
project. Set `GIT_EXTERNAL_DIFF` to point to your current build.

For example, you can run difftastic on its own source code.

```
$ GIT_EXTERNAL_DIFF=./target/release/difft git log -p --ext-diff -- src
```

### Output regression tests

`sample_files/` contains pairs of files (`foo_1.ext` and `foo_2.ext`)
that are diffed to catch unexpected changes in difftastic's output. CI
runs this comparison and fails if the result differs from
`sample_files/compare.expected`.

To run it locally:

```
$ just compare   # or: ./sample_files/compare_all.sh
```

If you changed difftastic's output on purpose, update the expected
results and commit them:

```
$ cp sample_files/compare.result sample_files/compare.expected
```

See [Adding A Parser](./adding_a_parser.md) for how to add new sample
files.

## Submitting changes

Difftastic is developed on GitHub. Open a pull request against the
`master` branch and make sure CI passes.

CI checks more than the test suite, so it's worth running the same
checks locally before you push:

- **Format:** `cargo fmt --all` (CI runs `cargo fmt --all -- --check`).
- **Tests:** `cargo test` and `cargo test -- --ignored`.
- **Spelling:** [`typos`](https://github.com/crate-ci/typos) (`cargo
  install typos-cli`, then run `typos`).
- **Output regression:** `just compare` (see above).

Difftastic pins its Rust toolchain in `rust-toolchain.toml`, so `rustup`
uses the right version automatically.

If your change is user-visible, add an entry to `CHANGELOG.md`.

## Logging

Difftastic uses the `pretty_env_logger` library to log some additional
debug information.

```
$ DFT_LOG=debug cargo run sample_files/old.jsx sample_files/new.jsx
```

See the [`env_logger`
documentation](https://docs.rs/env_logger/latest/env_logger/) for full details.

## Releasing

Releases are cut by tagging a version in git, which triggers the release
workflow on GitHub Actions. The `justfile` has a recipe that tags the
current version, pushes the tag, and bumps the version for the next
cycle:

```
$ just release
```

Add a new entry to `CHANGELOG.md` describing the release before tagging,
so it's included in the generated release notes.
